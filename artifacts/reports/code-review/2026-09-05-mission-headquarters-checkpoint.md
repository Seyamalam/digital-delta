# Mission headquarters checkpoint

Date: September 5, 2026. Baseline: `495f6c2`.

Scope: Android planning publication, the Hono presentation boundary, and per-mission
headquarters views. This is a software checkpoint, not completion of the fair build
or a new full-project security review.

## Implemented

- The dashboard indexes routes and rendezvous by mission. Selection survives
  incoming updates and sidebar navigation. Stream replacement clears it.
- A route arriving before its request still appears in the register. Legacy routes
  without mission IDs are not silently attached to another request.
- Android atomically records `RoutePlanned` and `SlaEvaluated`. The latter references
  the exact route event and includes breach, within-SLA, or no-route state.
- The observer allowlist rejects unknown/private fields, missing route references,
  invalid priority/SLA combinations and contradictory evaluation numbers.
- The dashboard matches mission, route, publisher and simulation provenance before
  using an evaluation. Publication ordering does not require the route to arrive
  before its evaluation.
- Five-minute-old estimates require replanning. Future timestamps are flagged.
  No route has no ETA. A same-origin/destination plan explicitly permits zero travel
  without implying that a handoff occurred.
- The bilingual register places selection before detail on smaller projectors and
  uses two columns on wider ones. The map follows the selected mission and displays
  its SLA/freshness and simulation labels.

## Bugs found during verification

1. Empty-feed selection dereferenced an absent evaluation. Corrected and covered by
   the rendered workspace tests.
2. A fresh SSE event was compared with the previous 30-second display-clock tick,
   briefly producing a false clock warning. Reception now refreshes the comparison
   clock. A regression test sends a new event between ticks.
3. An empty edge list conflated an unreachable destination with a same-node journey.
   Android now emits `ALREADY_AT_DESTINATION` for the latter; projection and connected
   tests cover the distinction.
4. The first layout put mission selection below a large summary. The revised layout
   keeps the register first and uses a side detail panel at wide resolutions.

## Evidence

Local gate: `scripts/verify-local.sh --connected`, JDK 17, emulator-5554,
Pixel_10_Pro_XL AVD, Android 16. This is not a physical 4 GB phone.

The checkpoint records test totals and the final gate result in `docs/TESTING.md`.
The gate covers JVM and connected Android tests, debug/minified release builds,
Go race/vet/build checks, Protobuf compatibility, bundled localization/map/model
checks, dashboard tests/typecheck/production build and Worker tests/typecheck/dry run.

Manual browser checks used the built Next.js app on loopback, a separate local
Hono/D1 store, and Argent-controlled Chromium. `observer-mission-qa.mjs` published
explicitly simulated fixture events through the real authenticated HTTP endpoint.
These browser events were not generated by physical phones.

Observed: two mission rows with distinct plans; selection unchanged when another
mission replanned; selection retained on the map route; a warning recovering to
within-SLA; no-route clearing ETA; and no false clock warning on new updates.
The 1366×768 and 1920×1080 register checks had no document-level horizontal overflow.
Screenshots and their limitations are in
`artifacts/screenshots/headquarters/2026-09-05-missions/README.md`.

## Still open

1. Operational fleet/preemption confirmation for accepted requests. The existing
   exercise still uses seeded cargo, vehicles and safe-waypoint assumptions. This
   checkpoint does not convert that into a real dispatch workflow.
2. General origin/destination selection against the offline graph, plus generalized
   post-handoff reassignment and recovery. Original request destinations are labeled
   as such in headquarters; a later edit is not inferred from them.
3. Live bilingual coordinator assignment/reconciliation dialog checks.
4. Physical three-phone radio/recovery, camera provisioning/PoD, encrypted backlog
   recovery, target-phone RAM/latency measurements and three unchanged offline passes.
5. Updated final report/pitch claims, human accessibility review and hosted deployment
   review. No remote Worker or Vercel deployment was performed for this checkpoint.

The next fleet slice needs accepted mission snapshots, a provisioned operator and
route-version checks, conflict-aware confirmation, and explicit custody transitions.
A suggested deposit must not mark cargo deposited until an authorized person confirms
the actual handoff. No additional sensors or vehicle hardware are needed or assumed.
