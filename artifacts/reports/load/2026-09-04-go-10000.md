# Go node 10,000-connection load evidence

Status: **Passed locally on 2026-09-04 at 12:11 Asia/Dhaka.**

This is measured engineering evidence for the required 10,000 simulated concurrent connections. It is not a claim about production disaster-area radio performance.

## Workload

- 10,000 independent gRPC client connections to `NodeMeshService.Synchronize` over IPv4 loopback.
- One bidirectional HTTP/2 stream per connection.
- One unique Protobuf `Envelope` sent per stream and durably written to a fresh Bolt database.
- Each client required a matching `DURABLY_STORED` acknowledgement.
- All 10,000 acknowledged streams remained open together for five seconds.
- Connections started across a ten-second ramp; the overall timeout was three minutes.
- The workload exercised connection handling, Protobuf parsing, stream receive/send, deduplication, Bolt persistence, and acknowledgements. It did not include recipient encryption or a lossy wireless link.

Command:

```bash
scripts/load-test-10000.sh 10000
```

## Interpretation and limits

The node met the concurrent-connection count, but the latency distribution shows that the single durable Bolt write path is throughput-bound under a synchronized 10,000-client burst. The p95 acknowledgement latency of 57.645 seconds is acceptable only as capacity evidence, not as an operational latency target. Production hardening should batch persistence or partition writers before claiming high-throughput deployment readiness.

This run does not reproduce Bluetooth/Wi-Fi Direct contention, packet loss, handset thermal limits, geographic distance, TLS overhead, long-lived message churn, or multiple server hosts. Those are separate physical and soak-test requirements. The script deliberately deletes its temporary keys/data and does not modify a demo database.
